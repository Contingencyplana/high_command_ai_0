# **Stage 3 — Azure Cloud Deployment**

**Five Stages Doctrine · High Command**

**Status:** Draft Active
**Purpose:** Define the conditions and guardrails for the first live Azure Cloud execution of Nightlands systems.
**Scope:** All ten genesis workspaces.

---

## **1. Mission**

Stage 3 is the moment Nightlands officially **moves into Azure Cloud**.

This stage begins only when each of the 10 genesis workspaces reaches:

### **✔ Two Deltas (32 Alfas)**

This is the threshold at which the system:

* becomes resilient to distributed execution
* can absorb cloud-level variability
* handles parallel workflows safely
* begins to generate meaningful telemetry at cloud scale

**Azure Cloud becomes active in Stage 3 — but exposure remains internal and non-human.**

There is still:

* **no embodiment**
* **no UI**
* **no testers**
* **no battlegrid actions**

Stage 3 is pure **runtime cloud activation** under strict safety discipline.

---

## **2. Why Two Deltas?**

A single Delta (16 Alfas) is stable enough for readiness (Stage 2), but **not** for distributed cloud execution.

Two Deltas (32 Alfas) provide:

### **1. Cross-cluster agreement**

Two independent clusters verify all outputs and detect drift instantly.

### **2. Distributed-state stability**

Cloud latency can cause divergence — two Deltas prevent silent corruption.

### **3. Emergence detection**

Cloud execution can amplify side effects; dual Deltas catch patterns early.

### **4. Reliability under parallel execution**

More Alfas = more channels = safer automatic correction.

### **5. Natural containment**

If 1 Delta fails, the second prevents cascades.

This is the minimum requirement for safe cloud activation.

---

## **3. What Changes in Stage 3?**

### **Allowed**

* **Cloud execution of Nightlands systems**
* Azure-based workflows
* Cloud hydration of Alfas (still Codex-only)
* Telemetry routed to Azure logs + local mirrors
* Distributed contract verification
* Multi-region deployment simulations
* Cloud-based build pipelines (disabled outside contracts)

### **Still Not Allowed**

* No battlegrid embodiment
* No rituals
* No game UI
* No testers or play input of any kind
* No Outlands overlays powered by cloud rendering
* No cloud-initiated agent creation
* No multiplayer or network clients

### Summary:

**Stage 3 = Cloud Active, Humans Absent.**

---

## **4. Mandatory Requirements for Stage 3 Activation**

Before cloud execution begins, each workspace must meet:

### **Per Workspace Requirements**

* **✔ Two Deltas (32 Alfas)**
* **✔ All 32 documented in Toyfoundry metadata**
* **✔ Delta-level telemetry stable for 72 hours**
* **✔ Toysoldiers validate cloud-ready ops**
* **✔ Valiant Citadel approves cloud safety**
* **✔ No known schema drift across 10 workspaces**

### **Cloud Requirements**

* **✔ Azure infrastructure online and fully configured**
* **✔ Cloud telemetry pipeline active**
* **✔ Logging, diagnostics, and monitoring enabled**
* **✔ Cloud Sync reconciled with Offline Sync**
* **✔ Deployment scripts reviewed by Toyfoundry**

### **Codex Requirements**

* **✔ All Alfas still Codex-only generated**
* **✔ No cloud auto-generation or self-deployment**
* **✔ No embodiment allowed prior to Stage 4**

---

## **5. Stage 3 Rules of Operation**

### **1. Cloud Mirroring**

Cloud and local runtimes must remain identical.
Local is always the source of truth.

### **2. No Autonomous Cloud Agents**

Alfas cannot spawn new agents or mutate deployment surroundings.

### **3. Cloud Execution Must Be Pauseable**

Human overrides must terminate cloud runtimes instantly.

### **4. Telemetry Quilt Requirements**

Every cloud action must log:

* timestamp
* workspace
* cluster
* Alfa ID
* contract results
* state checksum

### **5. Contract Discipline**

Every cloud call passes through Toyfoundry validation.

### **6. Drift Detection**

Dual Deltas must agree on:

* output
* state
* telemetry
* contract outcomes

Disagreement triggers auto-halt.

### **7. Cloud Failure Must Not Cause Local Failure**

Cloud is additive, never mandatory.

---

## **6. Transition Criteria to Stage 4**

Stage 3 ends only when:

* cloud execution is stable across all workspaces
* no new drift patterns emerge
* telemetry from cloud matches telemetry from local
* two Deltas consistently remain in agreement
* cloud logs show no anomalies
* distributed environments behave predictably
* cloud workflows survive load tests

Only then may High Command authorize:

### **Stage 4 — Internal Testers**

**(Requires one Echo = 4 Deltas = 64 Alfas per workspace)**

---

## **7. Summary**

Stage 3 transitions Nightlands from a **local-only system** to a **fully cloud-executing system**, while ensuring:

* **Two Deltas per workspace (32 Alfas)**
* **Contract-validated cloud execution**
* **Strict safety controls on all distributed workflows**
* **No gameplay, no humans, no embodiment**
* **100% telemetry coverage**
* **Manual override always available**

Stage 3 is where the system becomes **distributed**, but not yet **experienced**.
